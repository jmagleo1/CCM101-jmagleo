## REFLECTION
Object storage is way better than block storage for storing millions of photos because of how differently they organize data. Block storage splits files into fixed-size blocks tied to a specific file system, which works fine for things like operating systems but gets messy once you're dealing with huge amounts of files. Object storage treats each photo as a whole "object" with its own metadata and unique ID, spread across multiple servers instead of just one. This makes it way easier to scale — companies can just add more storage nodes instead of reorganizing everything, which is perfect for millions of client photos.
Docker made deploying MinIO less stressful, but it wasn't totally smooth. My first try using the official minio/minio image failed with an "unauthorized" error, and switching to quay.io/minio/minio gave the exact same error. Turns out MinIO recently restricted access to their official images due to licensing changes. I had to find an alternative and used pgsty/minio, a community-maintained fork, which finally worked. It was frustrating at first, but it taught me more than if everything just worked on the first try.
A "bucket" is basically like a main folder where you store your objects/files in cloud storage. I messed this up too — I accidentally named my bucket "jelo" instead of "client-photos," and found out MinIO doesn't let you rename a bucket, so I had to delete it and create a new one with the correct name.
For enterprise companies, I think they avoid losing data during a server crash by keeping multiple copies across different servers or locations, so if one goes down, the data is still safe somewhere else.
As for my confidence with the Linux command line, it's growing faster than I thought. Having to fix real errors instead of just following steps made me actually pay attention to what the terminal was telling me.
